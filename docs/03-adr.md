# 架构决策记录（ADR）

## 决策总览

| ADR | 决策 | 状态 | 主要收益 | 主要代价 |
|---|---|---|---|---|
| ADR-001 | 分层模块化单体 | 已采纳 | 边界清晰、构建简单、调试成本低 | 运行时仍是单进程，不能独立扩展模块 |
| ADR-002 | 类型级稀疏集合 ECS | 已采纳 | O(1) 组件访问、实现可解释、易测试 | 查询需要手工组合，不如 Archetype 高效 |
| ADR-003 | 固定 C ABI + C# NativeAOT | 已采纳 | 语言隔离、无 CLR 托管 C++ 互操作负担、异常受控 | 需要手写 ABI 镜像，不支持热重载 |
| ADR-004 | Play 模式整场景快照 | 已采纳 | 停止恢复语义简单、可靠 | 大型场景复制成本高，运行时修改不写回 |
| ADR-005 | 自研受限物理 | 已采纳 | 范围可控、可测试、适合课程设计 | 不支持复杂刚体和旋转 OBB |
| ADR-006 | RenderFrame 与渲染后端解耦 | 已采纳 | ECS 不接触 OpenGL，后端可替换 | 每帧需要构建中间描述数据 |
| ADR-007 | 固定步长、单线程 | 已采纳 | 行为确定、避免并发竞态、易复现 | CPU 利用率有限，不能利用多核 |
| ADR-008 | 组合根显式装配 | 已采纳 | 依赖可见、便于替换和测试 | 应用层构造代码比单例方案更长 |

## ADR-001：分层模块化单体

| 字段 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 背景 | 2–3 人、8–12 周课程设计，需要展示架构质量但不能承担分布式或微内核工程的集成成本 |
| 决策 | 使用 CMake 静态库形成模块边界，一个可执行文件作为组合根；模块之间只通过公共头文件和接口依赖 |
| 替代方案 | 单文件/单工程式引擎、微服务式编辑器、运行时动态模块系统 |
| 选择理由 | 模块边界仍可被编译器和代码审查验证；构建、调试、演示路径最短 |
| 后果 | 模块不能独立部署；若未来需要插件化运行时模块，需要新增动态模块 ABI |

## ADR-002：类型级稀疏集合 ECS

| 字段 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 背景 | 需要稳定实体句柄、可增删组件、可快照复制；课程设计不追求大规模 Archetype 性能 |
| 决策 | `World` 维护 generation 槽位；每个组件类型拥有独立 `SparseSet<T>`；删除使用 swap-and-pop |
| 替代方案 | 第三方 ECS（EnTT）、Archetype ECS、纯对象继承模型 |
| 选择理由 | 代码量可控；查找/增删语义清晰；可以直接对组件池做序列化和复制；便于用单元测试证明正确性 |
| 后果 | 多组件查询需要手工获取多个池；没有自动查询缓存和系统调度器 |

## ADR-003：固定 C ABI + C# NativeAOT

| 字段 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 背景 | 需要展示 C++ 核心与高层玩法脚本的边界，同时避免托管 C++、CLR 嵌入和跨语言异常 |
| 决策 | C# 使用 .NET 10 NativeAOT 发布 DLL；导出固定的 C ABI；C++ 传入只读 `EngineApiV1` 函数表；字符串使用 UTF-8 指针+长度；句柄使用 64 位整数 |
| 替代方案 | C++ 直接编译玩法、Lua 脚本、托管 C++/CLI、嵌入 CoreCLR |
| 选择理由 | ABI 稳定、边界小、无 CLR 托管层；C# 异常在导出函数内捕获；NativeAOT 产物可像普通 DLL 一样加载 |
| 后果 | 需要手工维护 C++/C# 两份结构布局；修改字段必须遵守追加规则或提升 ABI 版本；不支持热重载和程序集卸载 |

### ABI 兼容规则

| 规则 | 说明 |
|---|---|
| 版本校验 | 插件导出 `L3D_ScriptAbiVersion` 必须等于宿主 `L3D_SCRIPT_ABI_VERSION` |
| 结构大小 | C# 检查 `structSize >= sizeof(EngineApiV1)`，拒绝旧布局 |
| 字段追加 | 当前 V1 在定稿前以追加字段方式扩展；不得重排、删除或改变已有字段语义 |
| 异常 | 所有 C# 导出函数必须捕获异常，禁止跨 ABI 抛出 |
| 生命周期 | DLL 不卸载；修改 C# 后重启引擎 |

## ADR-004：Play 模式整场景快照

| 字段 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 背景 | 编辑器和运行时共享一个 World，但 Play 期间的移动、销毁实体和脚本修改不应污染作者场景 |
| 决策 | `EditorSession::beginPlay` 深拷贝整个 World；停止时用备份 World 整体替换当前 World，并重新绑定事件总线 |
| 替代方案 | 运行时与编辑场景双 World、命令日志撤销、属性级差异恢复 |
| 选择理由 | 恢复语义完整；不需要为每种组件编写逆操作；测试容易验证 |
| 后果 | 大场景需要额外内存和复制时间；Play 期间不能直接从运行时 World 写回作者场景 |

## ADR-005：自研受限物理

| 字段 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 背景 | 示例闭环只需要角色移动、世界轴碰撞、触发器和射线；引入通用刚体库会增加接口和调试面 |
| 决策 | 实现世界轴 AABB、球体、角色 AABB、重力、跳跃、触发器和最近射线命中；不实现旋转 OBB、关节和角动量 |
| 替代方案 | Jolt、Bullet、PhysX、自研完整刚体 |
| 选择理由 | 行为可解释、测试可精确构造；代码量与课程周期匹配 |
| 后果 | 不能用于复杂物理玩法；需要通过 `IPhysicsWorld` 预留替换点 |

## ADR-006：RenderFrame 与渲染后端解耦

| 字段 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 背景 | 场景层若直接调用 OpenGL，会导致 ECS 与图形 API 强耦合，编辑器视口也难以复用 |
| 决策 | 场景层只提取 `RenderFrame`（view/projection、光照、RenderItem）；`IRenderer` 消费 RenderFrame；OpenGL 类型只出现在渲染器内部 |
| 替代方案 | ECS 直接持有 GL 资源、渲染系统直接遍历 World |
| 选择理由 | 场景层可独立测试；渲染后端可替换；编辑器相机和运行时相机复用同一提取流程 |
| 后果 | 每帧构建中间数组和 GUID 字符串；需要额外的资产/GPU 缓存映射 |

## ADR-007：固定步长、单线程

| 字段 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 背景 | 课程设计需要稳定、可重复的模拟行为和简单的调试路径 |
| 决策 | 模拟固定 60 Hz，单帧最多 5 步；输入、脚本、物理、渲染和 UI 全部在主线程 |
| 替代方案 | 可变步长、Job System、物理线程、渲染线程 |
| 选择理由 | 无竞态；事件派发顺序确定；测试可在无窗口下复现固定步行为 |
| 后果 | 性能上限受单核约束；高帧率渲染不会提高模拟精度 |

## ADR-008：组合根显式装配

| 字段 | 内容 |
|---|---|
| 状态 | 已采纳 |
| 背景 | 使用全局单例或服务定位器会隐藏依赖，使替换和测试困难 |
| 决策 | `Application` 是唯一组合根；按顺序构造 Window、AssetDatabase、Renderer、ScriptHost、World、Editor；通过接口注入依赖 |
| 替代方案 | 全局服务容器、静态单例、模块自行初始化 |
| 选择理由 | 生命周期和初始化顺序显式；便于替换实现；依赖关系可从构造代码直接读出 |
| 后果 | 应用层代码量增加；新增子系统需要修改组合根 |

## 决策之间的关系

```text
模块化单体（ADR-001）
  ├─ 需要接口隔离与组合根（ADR-008）
  ├─ 选择稀疏 ECS 作为运行时数据模型（ADR-002）
  ├─ 选择 RenderFrame 作为场景/渲染边界（ADR-006）
  ├─ 选择固定 C ABI 作为脚本边界（ADR-003）
  └─ 选择自研受限物理作为可替换子系统（ADR-005）

固定步长/单线程（ADR-007）
  └─ 为 Play 快照（ADR-004）和确定性测试提供简单前提
```
